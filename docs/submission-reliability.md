# 草稿恢复与提交重试

## 浏览器草稿

草稿由 `src/assessment-draft.ts` 管理，继续使用按量表版本隔离的 localStorage 键，内容为 `{ answers, submissionId }`。

- 未完成时刷新，恢复到第一道未答题。
- 已完成但未收到成功结果时刷新，保留全部答案和同一提交编号，恢复到最后一题。
- 兼容以前只有答案对象的草稿，完整旧草稿也不会丢失。
- 提交前持久化当前编号；网络失败、响应解析失败不会清除草稿。
- 收到成功结果后清除对应草稿；用户明确开始新测评时创建新草稿和编号。
- 修改答案或重新随机作答会生成新的编号。重新完成一次独立测评，即使答案或分数相同，也会分别记录。
- 成功写入后的动画错误不会被当作保存失败，再次引导用户提交。
- 提交从请求发出到响应正文读取、校验完成共等待最多 30 秒；超时取消客户端请求、保留答案和原编号并恢复操作。客户端超时不表示服务端一定未写入，重试仍由原编号返回已保存结果。
- 提交响应只更新发起提交的页面版本。等待时后退、前进或开始新测评，不会被迟到响应强制跳页；成功响应只清理它自己的草稿，不清除其他提交。失败处理与状态恢复不依赖当前页面仍有原来的按钮或消息元素。

## 后端回执

业务记录表 `results` 保存自增 `id`、开放性 `openness`、尽责性 `conscientiousness`、外向性 `extraversion`、宜人性 `agreeableness`、神经质 `neuroticism`、结果链接和写入/更新时间；五个分数为 0–100 的整数，已取代 `result_json`。

技术回执放在独立的 `submission_receipts` 表：

| 字段 | 用途 |
|---|---|
| `request_id` | 请求 UUID，唯一匹配同一次提交，统一为小写 |
| `request_fingerprint` | 量表版本及规范化答案的 SHA-256 摘要，不保存逐题答案 |
| `result_id` | 对应的结果自增序号，外键关联 `results.id` |

服务端在同一个 `BEGIN IMMEDIATE` 事务中检查回执并写入结果、回执。两者必须同时成功；任何一步失败都会回滚。不同连接也依靠数据库事务串行化检查和写入。

- 新编号：新增业务记录和回执。
- 相同编号、相同内容：返回原始链接，记录数、写入时间、更新时间均不变。
- 相同编号、不同答案：返回 409，包括不同答案恰好计算出相同分数的情况。
- 不同编号、相同分数：分别写入业务记录。
- 返回结果前网络断开：客户端可使用原编号重试；服务重启后回执仍保留。

回执仅在提交时访问。已有结果链接继续由后端直接解密，访问结果不查询数据库。

## 数据维护

两张表位于同一个 SQLite 文件中，数据库备份会一起保存。技术回执通过外键 `ON DELETE CASCADE` 关联结果；通过外部 SQLite 工具清理记录时须启用 `PRAGMA foreign_keys = ON`，以免留下孤立回执。

本次之前的记录没有保存提交编号，无法可靠识别过去的重试，保留原记录，不按分数猜测或删除历史数据。新逻辑从更新后成功写入的提交开始提供持久重试保护。

加密密钥和旧链接映射仍按原有规则随数据库一起备份、迁移。

启动时先以只读方式校验已有的每一条加密结果。密钥缺失、与结果不匹配或已有加密链接损坏时停止启动，避免继续写入另一份密钥产生的结果。此检查只在启动时执行，结果链接访问仍直接解密、不查询数据库。

## 服务关停

收到 SIGTERM 或 SIGINT 后停止接受新连接，在途 HTTP 请求继续接收请求体、完成事务并发送响应，再关闭数据库。响应使用 `Connection: close`，避免完成的请求继续占用保活连接。钉钉工作进程停止取任务，取消当前远端请求并保留可重试的队列状态。

默认最多等待 15 秒；超时会关闭未完成连接，再等待处理函数退出并关闭数据库。未收到结果的客户端用原编号重试。Compose 的停止宽限期为 25 秒，覆盖应用等待与资源清理。直接运行 Node 时可通过 `SHUTDOWN_TIMEOUT_MS` 调整等待期限；自定义容器运行配置时应同步设置更长的容器停止宽限期。
