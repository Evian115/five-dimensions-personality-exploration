## 已复现的问题

### 1. 同时开两个作答标签页，旧页面可覆盖较新的进度

位置：`src/main.ts:321` 的 change 回调、`src/assessment-draft.ts:8`。

两个标签页持有各自的内存答案，但使用同一个 localStorage 键；保存时直接覆盖完整草稿，未检测存储中是否已有更新的版本。

复现：A 页保存前 5 题，B 页从同一草稿继续答到第 10 题；A 页再回答第 6 题，存储中的答案从 10 题退回 6 题。刷新 B 页后恢复到第 7 题，第 7–10 题已丢失。

建议：保存前检测草稿身份与版本；发现另一个页面更新时提示恢复或停止覆盖。不能简单把不同草稿无条件合并。

### 2. HTTP 200 但结果字段缺失时，完整草稿会被清除后页面报错

位置：`src/main.ts:118` 的 `readJson()`，以及 `src/main.ts:190` 开始的成功处理。

`readJson()` 只检查 JSON 能否解析及 HTTP 状态，`as SavedResult` 没有运行时校验。请求返回 HTTP 200、正文 `{}` 时会进入成功分支，先调用 `completeDraft()` 清除草稿，随后在结果渲染时读取缺失的 scores，抛出 `Cannot read properties of undefined (reading 'O')`。

故障注入复现：后端先成功写入，再把浏览器收到的响应替换为 HTTP 200 `{}`；原 60 题草稿被删除，结果页未能正常显示。正常后端会返回完整结构，这属于异常响应容错缺陷，不表示目前每次提交都会触发。

建议：清除草稿前校验完整结果结构、可用的结果路径及关键分数；校验失败保留原提交编号和草稿，允许幂等重试。

### 3. 本地存储写入异常会让有效的结果链接白屏

位置：`src/main.ts:20`，`src/assessment-draft.ts:8`、`:29`。

结果页也会先恢复并写入作答草稿。`restoreDraft()` 的读取异常会捕获，但后续 `saveDraft()` 的 setItem 不在保护内。浏览器存储不可用或写入抛出 QuotaExceededError 时，主模块在渲染前中断。

复现：在隔离浏览器中让草稿键的 setItem 抛出 QuotaExceededError，再访问一个真实有效的结果链接；出现未捕获错误，`#app` 中没有页面元素，结果读取未执行。

建议：将只读结果展示与草稿初始化解耦；为存储不可用提供可见提示和受控降级，不要静默承诺刷新仍能恢复。

### 4. 已有数据却丢失密钥时，启动过程会静默生成新密钥

位置：`server/result-cipher.ts:15`，`server/store.ts:26`。

当前只按密钥文件是否存在决定是否新建，没有区别“首次部署”和“恢复时遗漏密钥”。

复现：在临时库保存一个结果，关闭 store，仅移除临时密钥后重新打开。服务仍可启动并接受新提交，但旧链接无法解密，同一旧提交编号的重试也因解密原链接失败而报错。

密钥丢失后无法仅凭数据库恢复旧密文，这是加密机制本身的限制。这里需要改进的是启动保护：发现已有加密结果或回执却缺少密钥时，应明确拒绝启动并提示恢复原密钥，避免误以为恢复成功。空库首次启动仍应正常生成密钥。
